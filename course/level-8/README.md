# Блок 8. Продакшн-сборка и деплой

**Место в курсе:** финальный, завершающий блок. Вы реализовали все компоненты интеллектуальной инженерной системы — MCP‑серверы для Компас‑3D и лазерного гравировщика CarverAll 15Pro, эмуляторы оборудования, универсальный ToolCallingClient и терминальный оркестратор на базе OpenCode. Теперь пора превратить набор исходников в продукт, готовый к запуску в реальной среде: на рабочей станции инженера, на удалённом сервере или в изолированных контейнерах.

**Глобальная цель Блока 8:** Научить вас упаковывать агентную систему в контейнеры, настраивать альтернативный HTTP‑транспорт для MCP, разворачивать все компоненты единообразно, настраивать логирование и мониторинг, а также подготовить демонстрационный стенд для итоговой презентации проекта заказчику или для портфолио.

Вы пройдёте три модуля:

1. **Контейнеризация MCP‑серверов и эмуляторов** — изолируем зависимости и обеспечиваем простой запуск.
2. **Развёртывание оркестратора и серверов** — деплоим всё на локальную машину или VPS, пишем сценарий развёртывания.
3. **Мониторинг, логирование и итоговая демонстрация** — добавляем продакшн‑наблюдаемость, готовим сквозной сценарий и оформляем репозиторий.

## Модуль 8.1. Контейнеризация MCP-серверов и эмуляторов

### Теория

#### Зачем нам контейнеры
Контейнеризация решает сразу несколько проблем промышленной эксплуатации:

- **Изоляция зависимостей.** Каждый компонент (MCP‑сервер, эмулятор) живёт в своём окружении со строго определёнными версиями Node.js, библиотек и системных пакетов. Больше нет «у меня не запускается, потому что Node 18, а нужна 20».
- **Простота развёртывания.** Вместо многостраничной инструкции по установке достаточно трёх команд: `docker compose build`, `docker compose up`. Запуск идентичен на Mac, Windows, Linux и в CI/CD.
- **Единообразие окружения.** Вся команда и серверное окружение используют одинаковые образы. Это кардинально снижает «магию» окружения.

#### Docker для Node.js/TypeScript: многоступенчатая сборка
Наша цель — минимальный production‑образ. Нам не нужны dev‑зависимости, исходный TypeScript и компилятор. Поэтому используем **multi‑stage build**:

- **Этап builder** — на базе `node:20-alpine` (или полновесного образа, если нужны нативные модули) ставим *все* зависимости, копируем исходники и компилируем TS в JS (`dist/`).
- **Этап production** — начинаем с чистого `node:20-alpine`, копируем `dist/` и ставим только production‑зависимости (`npm ci --omit=dev`). Размер образа сокращается в разы.

#### Особенности MCP-серверов в контейнерах
MCP по умолчанию работает поверх `stdio`: JSON‑RPC сообщения ходят через стандартные потоки ввода/вывода. При запуске контейнера эти потоки можно пробросить, поэтому такой сервер запускается как обычный процесс внутри контейнера:

```dockerfile
ENTRYPOINT ["node", "dist/index.js"]
```

Но в распределённой системе удобнее использовать **HTTP‑транспорт** (например, Server‑Sent Events или WebSocket). Тогда MCP‑сервер становится долгоживущим сетевым сервисом, слушающим порт. В контейнере это требует открытого порта и отдельной точки входа, запускающей сервер с флагом `--transport http`.

#### Эмуляторы в контейнерах
Эмуляторы оборудования (Компас‑3D, CarverAll) — это тоже Node.js‑приложения с HTTP‑интерфейсом. Упаковав их в контейнеры, мы получаем самодостаточные сервисы, которые можно запустить одной командой и не заботиться о портах и зависимостях на хосте.

### Практика

#### Структура проекта перед началом
Предположим, в корне вашего проекта лежат:

```
/kompas3d-mcp
/carverall-mcp
/kompas3d-emulator
/carverall-emulator
/opencode-config
/tooling-client   // ToolCallingClient
...
```

Каждый каталог содержит `package.json`, `tsconfig.json`, исходный код.

#### 8.1.1. Dockerfile для kompas3d-mcp
Создадим `kompas3d-mcp/Dockerfile`:

```dockerfile
# --- Этап сборки ---
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build   # предполагается, что скрипт build компилирует TS → dist/

# --- Этап production ---
FROM node:20-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/package*.json ./
RUN npm ci --omit=dev && npm cache clean --force
# Для stdio-транспорта просто запускаем сервер
ENTRYPOINT ["node", "dist/index.js"]
```

**Важно:** убедитесь, что `npm run build` создаёт папку `dist` с точкой входа `dist/index.js`. В TypeScript‑проектах настройте `tsconfig.json`: `"outDir": "./dist"`.

#### 8.1.2. Dockerfile с HTTP‑транспортом
Если вы хотите запускать MCP‑сервер как долгоживущий HTTP‑сервис, создайте `kompas3d-mcp/Dockerfile.http`:

```dockerfile
FROM kompas3d-mcp:latest   # используем базовый образ
EXPOSE 3000
ENTRYPOINT ["node", "dist/index.js", "--transport", "http", "--port", "3000"]
```

Либо объедините оба режима в одном Dockerfile, передавая переменную окружения `TRANSPORT`. Но для учебной ясности сделаем отдельные файлы.

#### 8.1.3. Эмуляторы
Эмулятор Компас‑3D уже умеет принимать HTTP‑запросы на некотором порту (допустим, 3001). Его `kompas3d-emulator/Dockerfile`:

```dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/package*.json ./
RUN npm ci --omit=dev && npm cache clean --force
EXPOSE 3001
CMD ["node", "dist/index.js"]  # эмулятор сам поднимает HTTP
```

Аналогично `carverall-emulator/Dockerfile` (порт 3002).

#### 8.1.4. docker-compose.yml для всей системы
Создадим `docker-compose.yml` в корне проекта. Выберем комбинированный подход:

- **Эмуляторы** запускаем как контейнеры (долгоживущие HTTP‑сервисы).
- **MCP‑серверы** пока оставим локальными, работающими через stdio как дочерние процессы оркестратора. При желании позже можно переключиться на HTTP‑контейнеры.

```yaml
version: "3.8"
services:
  kompas-emulator:
    build: ./kompas3d-emulator
    ports:
      - "3001:3001"
    restart: unless-stopped

  carverall-emulator:
    build: ./carverall-emulator
    ports:
      - "3002:3002"
    restart: unless-stopped

  # MCP-серверы в HTTP-режиме (опционально, пока закомментируем)
  # kompas-mcp:
  #   build:
  #     context: ./kompas3d-mcp
  #     dockerfile: Dockerfile.http
  #   ports:
  #     - "3000:3000"
  #   environment:
  #     - KOMPAS_EMULATOR_URL=http://kompas-emulator:3001
  #   depends_on:
  #     - kompas-emulator
  #
  # carverall-mcp:
  #   build:
  #     context: ./carverall-mcp
  #     dockerfile: Dockerfile.http
  #   ports:
  #     - "4000:4000"
  #   environment:
  #     - CARVERALL_EMULATOR_URL=http://carverall-emulator:3002
  #   depends_on:
  #     - carverall-emulator
```

Эмуляторы теперь запускаются одной командой `docker compose up -d`. MCP‑серверы будем запускать локально через OpenCode.

#### 8.1.5. Сборка и проверка
```bash
# Сборка образов
docker compose build

# Запуск эмуляторов в фоне
docker compose up -d

# Проверка доступности
curl http://localhost:3001/health
curl http://localhost:3002/health
```

Если эмуляторы отвечают, всё работает. Остановка: `docker compose down`.

**Типичные ошибки:**
- *Контейнер запускается и сразу падает.* Проверьте, что `dist/index.js` скопирован в образ. Запустите контейнер вручную с `docker run -it <image> sh` и убедитесь, что файл на месте.
- *Не находятся production‑зависимости.* Убедитесь, что вы скопировали `package.json` и `package-lock.json` перед `npm ci --omit=dev`. Если зависимости требуют нативной компиляции, возможно, нужен `node:20` вместо alpine (или установите `build-base`).
- *Порт эмулятора недоступен с хоста.* Проверьте проброс в `docker-compose.yml` и что приложение слушает `0.0.0.0`, а не `127.0.0.1`.
- *Сервер MCP не может подключиться к эмулятору по `localhost`.* Когда MCP‑сервер работает на хосте, а эмулятор в контейнере, используйте `localhost:3001`. Если MCP‑сервер тоже в контейнере, нужно использовать имя сервиса `http://kompas-emulator:3001`.

## Модуль 8.2. Развёртывание оркестратора и серверов

### Теория

#### Варианты деплоя
1. **Локальная машина инженера** — самый простой и частый случай. OpenCode запускается в терминале, MCP‑серверы как дочерние процессы (stdio). Эмуляторы — в Docker или даже локально. Такую схему мы реализуем в первую очередь.
2. **Удалённый сервер (VPS)** — OpenCode и всё окружение устанавливаются на сервер. Инженер подключается по SSH. Это превращает рабочую станцию в мощный сервер для тяжёлых задач (например, рендеринга).
3. **Полностью контейнеризированный вариант** — и оркестратор, и MCP‑серверы, и эмуляторы живут в контейнерах, общаются по HTTP. Такой вариант удобен для масштабирования, но для инженерного рабочего места избыточен.

#### Безопасность
API‑ключи к LLM (DeepSeek, YandexGPT) — это чувствительные данные. Никогда не храните их в образах или в репозитории. Используйте `.env` файл, который добавлен в `.gitignore`, либо монтируйте его при запуске контейнера. Для локального деплоя мы будем передавать переменные окружения напрямую.

#### Конфигурация окружения
Нам потребуются переменные:
- `DEEPSEEK_API_KEY`
- `YANDEX_API_KEY`
- `KOMPAS_EMULATOR_URL` (по умолчанию `http://localhost:3001`)
- `CARVERALL_EMULATOR_URL` (по умолчанию `http://localhost:3002`)

Они должны быть доступны оркестратору и MCP‑серверам.

---

### Практика

#### 8.2.1. Скрипт полного развёртывания (deploy.sh)
Создадим в корне проекта `deploy.sh` для Linux/macOS (и аналог `deploy.ps1` для Windows). Скрипт автоматизирует весь процесс: от установки зависимостей до запуска оркестратора.

```bash
#!/usr/bin/env bash
set -euo pipefail

echo "=== 1. Установка зависимостей MCP-серверов ==="
cd kompas3d-mcp && npm ci && npm run build && cd ..
cd carverall-mcp && npm ci && npm run build && cd ..
# ToolCallingClient, если нужно
cd tooling-client && npm ci && npm run build && cd ..

echo "=== 2. Запуск эмуляторов в Docker ==="
docker compose up -d

echo "=== 3. Ожидание готовности эмуляторов ==="
until curl -s http://localhost:3001/health > /dev/null; do sleep 0.5; done
until curl -s http://localhost:3002/health > /dev/null; do sleep 0.5; done
echo "Эмуляторы готовы."

echo "=== 4. Экспорт переменных окружения (замените на свои ключи) ==="
export DEEPSEEK_API_KEY="${DEEPSEEK_API_KEY:-your-deepseek-key}"
export YANDEX_API_KEY="${YANDEX_API_KEY:-your-yandex-key}"
export KOMPAS_EMULATOR_URL="http://localhost:3001"
export CARVERALL_EMULATOR_URL="http://localhost:3002"

echo "=== 5. Запуск OpenCode с конфигурацией ==="
# Предполагаем, что OpenCode установлен глобально или лежит в ./opencode
opencode run --config ./opencode-config/config.yaml
```

Сделайте файл исполняемым: `chmod +x deploy.sh`. Запуск: `./deploy.sh`.

**Примечания:**
- Скрипт компилирует MCP‑серверы, чтобы OpenCode мог их запускать через stdio.
- Путь к скомпилированному JS указывается в конфигурации OpenCode (например, `command: node /absolute/path/to/kompas3d-mcp/dist/index.js`). Убедитесь, что пути правильные.
- Для безопасности API‑ключи можно брать из системного окружения или из файла `.env`, который не коммитится.

#### 8.2.2. Конфигурация OpenCode для локального деплоя
В файле `opencode-config/config.yaml` укажите абсолютные пути к точкам входа MCP‑серверов:

```yaml
mcp_servers:
  kompas3d:
    command: node
    args:
      - "/home/user/project/kompas3d-mcp/dist/index.js"
    env:
      KOMPAS_EMULATOR_URL: "http://localhost:3001"
  carverall:
    command: node
    args:
      - "/home/user/project/carverall-mcp/dist/index.js"
    env:
      CARVERALL_EMULATOR_URL: "http://localhost:3002"
```

#### 8.2.3. Деплой на удалённый VPS (краткая инструкция)
1. Установите Node.js 20 и Docker на сервер.
2. Склонируйте репозиторий: `git clone ...`
3. Создайте `.env` с ключами.
4. Выполните `./deploy.sh`.
5. Для фонового режима можно использовать `tmux` или `systemd` для OpenCode.

#### 8.2.4. Оркестратор и MCP-серверы как службы (HTTP‑режим)
Если вы решили перевести MCP‑серверы на HTTP и контейнеризировать их, в `docker-compose.yml` раскомментируйте сервисы `kompas-mcp` и `carverall-mcp`. Тогда конфигурация OpenCode изменится: вместо команды запуска нужно указать URL:

```yaml
mcp_servers:
  kompas3d:
    transport: http
    url: "http://localhost:3000/sse"   # зависит от реализации
  carverall:
    transport: http
    url: "http://localhost:4000/sse"
```

В этом случае MCP‑серверы запустятся вместе с эмуляторами через `docker compose up -d`, и их не нужно компилировать отдельно.

**Запуск через systemd (для HTTP‑серверов на хосте, без Docker):**
Создайте unit‑файл, например `/etc/systemd/system/kompas-mcp.service`:

```
[Unit]
Description=Kompas3D MCP Server
After=network.target

[Service]
Type=simple
User=youruser
WorkingDirectory=/opt/project/kompas3d-mcp
ExecStart=/usr/bin/node dist/index.js --transport http --port 3000
Restart=always
Environment=KOMPAS_EMULATOR_URL=http://localhost:3001

[Install]
WantedBy=multi-user.target
```

Аналогично для CarverAll. Затем `systemctl enable` и `systemctl start`.

### Типичные ошибки
- *OpenCode не может найти MCP‑сервер.* Проверьте, что путь в `args` абсолютный и файл существует. При использовании `node` убедитесь, что Node установлен и доступен в `PATH`.
- *Эмулятор не отвечает.* Проверьте, что порты не заняты, контейнеры запущены (`docker ps`), health‑endpoint правильный.
- *Ошибка подключения к LLM.* API‑ключ не установлен или невалиден. Проверьте переменные окружения: `echo $DEEPSEEK_API_KEY`.
- *Права доступа.* Если скрипт не исполняется, `chmod +x deploy.sh`.

## Модуль 8.3. Мониторинг, логирование и итоговая демонстрация

### Теория

#### Зачем нужен мониторинг в агентных системах
Агентная система — это цепочка асинхронных вызовов: пользователь → оркестратор → LLM → function call → MCP‑сервер → эмулятор. Проблемы на любом уровне должны быть быстро обнаружены. Нам нужны:

- **Структурированные логи** для поиска и анализа.
- **Метрики** времени выполнения и ошибок, чтобы понимать узкие места.
- **Health‑check’и** зависимостей, чтобы не ждать таймаута.

#### Инструменты
- **pino** — быстрый логгер для Node.js с поддержкой JSON «из коробки». Лог в JSON легко парсить и отправлять в централизованные системы.
- **winston** — более тяжёлая альтернатива, тоже популярен. Мы выберем pino за минимализм.
- **OpenTelemetry** — стандарт распределённой трассировки. Может пригодиться для отслеживания запроса от оркестратора до инструментов, но в рамках курса мы ограничимся ручным логированием ключевых шагов.

#### Что логировать в MCP‑сервере
- Старт сервера (транспорт, порт/stdio).
- Каждый входящий JSON‑RPC запрос (название инструмента, параметры).
- Результат вызова (успех/ошибка, длительность, краткий результат).
- Ошибки соединения с эмулятором.
- Периодический health‑check эмулятора.

---

### Практика

#### 8.3.1. Добавление структурированного логирования в kompas3d-mcp
Установим pino: `npm install pino`. В точке входа `kompas3d-mcp/src/index.ts`:

```typescript
import pino from 'pino';

const logger = pino({
  level: process.env.LOG_LEVEL || 'info',
  transport: process.env.NODE_ENV !== 'production'
    ? { target: 'pino-pretty', options: { colorize: true } }
    : undefined,  // в production чистый JSON
});

logger.info({ transport: 'stdio' }, 'Kompas3D MCP server starting');
```

При инициализации инструментов оборачиваем каждый вызов:

```typescript
async function callTool(name: string, args: any) {
  const start = Date.now();
  logger.info({ tool: name, args }, 'tool_call_start');
  try {
    const result = await actualToolHandler(args);
    const duration = Date.now() - start;
    logger.info({ tool: name, duration, result: 'success' }, 'tool_call_success');
    return result;
  } catch (error) {
    const duration = Date.now() - start;
    logger.error({ tool: name, duration, error: error.message }, 'tool_call_failure');
    throw error;
  }
}
```

Аналогично добавим периодический health‑check эмулятора:

```typescript
setInterval(async () => {
  try {
    const res = await fetch(`${emulatorUrl}/health`);
    if (!res.ok) throw new Error(`status ${res.status}`);
    logger.debug('emulator_health_check_ok');
  } catch (err) {
    logger.error({ err: (err as Error).message }, 'emulator_health_check_failed');
  }
}, 30000); // раз в 30 секунд
```

#### 8.3.2. Вывод логов: stdout и файл
По умолчанию pino пишет в stdout. В production‑окружении логи часто собираются демоном (Docker log driver, journald). Можно также дописать транспорт для записи в файл. Простейший вариант — через `pino/file`:

```typescript
import pino from 'pino';
const logger = pino(
  pino.transport({
    targets: [
      { target: 'pino/file', options: { destination: '/var/log/kompas-mcp.log' } },
      { target: 'pino-pretty', options: { colorize: true } } // дубль в консоль
    ]
  })
);
```

#### 8.3.3. Health‑check эмуляторов
Мы уже предусмотрели эндпоинты `/health` в эмуляторах. Важно, чтобы они возвращали 200 и, возможно, JSON с информацией. MCP‑серверы используют этот эндпоинт для мониторинга. В docker‑compose также можно добавить `healthcheck`:

```yaml
services:
  kompas-emulator:
    ...
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3001/health"]
      interval: 10s
      timeout: 3s
      retries: 3
```

Это позволит `depends_on` с условием `service_healthy`.

#### 8.3.4. Итоговая демонстрация: сквозной сценарий
Кульминация всего курса — единый проход сценария от голосовой команды до готового изделия. Вы будете использовать оркестратор, чтобы выполнить:

> «Создай корпус для датчика с отверстиями, сохрани в DXF и выгравируй на оргстекле»

**Порядок действий:**
1. Запустите всю систему через `./deploy.sh` (или вручную по шагам).
2. Откройте OpenCode и введите промпт с задачей.
3. Оркестратор вызовет инструменты `create_detail` и `add_holes` в Kompas MCP, затем `export_dxf`.
4. Затем обратится к CarverAll MCP: `load_dxf`, `set_material` (оргстекло), `start_engraving`.
5. Все вызовы и ответы запишутся в логи в JSON.
6. Проверьте результаты: файл DXF появился в рабочей директории (или эмулятор его сгенерировал), гравировка отмечена как завершённая в эмуляторе.

**Снимите скринкаст** (можно с помощью OBS или встроенных средств macOS/Windows) продолжительностью до 5 минут. Покажите:
- запуск эмуляторов и MCP‑серверов,
- выполнение задачи в OpenCode,
- логи в реальном времени (хвост файла лога),
- итоговые артефакты.

### Типичные ошибки при мониторинге и демонстрации
- *Логи забивают консоль.* Используйте `pino-pretty` только в dev‑режиме, в production — чистый JSON.
- *Health‑check не работает в Docker.* Команда `curl` может отсутствовать в образе. Используйте `wget` или напишите простой Node‑скрипт для проверки.
- *При демонстрации забыли про API‑ключи.* Проверьте, что переменные экспортированы, или используйте `.env` с автоматической загрузкой (dotenv).
- *Неоднозначные пути.* В скринкасте показывайте абсолютные пути или стартуйте из фиксированной папки.
